# Amanda Askell 寓言学习法 —— 完整方法论与规划设计依据

本文件是 learn-plan / learn-lesson / learn-review 三个 skill 共享的方法论底座。
来源：Anthropic 研究员 Amanda Askell 的寓言提示法（fable prompt technique），
综合 appliedaihub.org 英文原版与雪球作者"赫燚Zeke"的中文阐释。

## 一、核心思想

最好的学习材料不是让 AI"解释"概念，而是让它"演出"概念。

- **定义是压缩**：丢弃了维度、情绪和后果，只剩下抽象标签。标签是思考的终点——
  一旦说"这不就是幸存者偏差嘛"，大脑就停止工作了。
- **故事是解压缩**：还原了动机、时间、对抗与遗憾。阅读故事时，大脑会追踪角色、
  推断动机、构建因果模型——当结尾概念被点明时，解释不再是新信息，
  而是在**确认读者刚刚亲身经历过的东西**。
- 这就是"反向费曼"：费曼法是"讲给小孩听"，Askell 法是"让 AI 把概念讲到
  你说不出它的名字、却懂了逻辑本身"。
- **理解一件事的标志，不再是能复述定义，而是能把它变回一个故事。**
- Prompt 不是提问，而是一条设计好的认知路径。直接问"X 是什么"，得到的是
  定义→例子→注意事项的平庸序列；指定"先叙事、先考验读者、再揭示、后回扣"，
  是在设计理解到达的顺序。

## 二、标准流程（learn-lesson 的寓言四步）

以"我想搞懂 X"为输入：

1. **找一个相近但更冷门的原理**：不直接讲 X，先找一个跟 X 很相近、
   但"本科生不了解、研究生才懂"的小众原理来做故事载体。
   - 为什么：刻意设置难度。太通俗的概念（如直接用"择优录取"讲排序）没有启发；
     太艰深又过于遥远。相近而冷门的原理，读者既没有现成标签可贴，
     又能顺着相似性迁移到 X 上。
   - 泰勒·考恩：平庸的问题只能得到平庸的答案。AI 的训练分布决定了它的
     "中心位置"永远是平庸的——要偏离轴心，问题必须足够具体。
2. **三段式故事**：用约三段话把那个原理演出来。要求：
   - 有冲突、有压力，让读者感受到当事人在做什么样的**取舍**；
   - **全程不许出现概念的名字**（X 和载体原理都不许）；
   - 故事完全体现概念，理想情况下读者接近结尾才隐约意识到在讲什么。
3. **先问后揭示（互动式延迟命名）**：故事讲完后先不揭晓，
   先问读者："**你觉得这个故事在讲什么道理？**"
   - 等读者作答之后再揭晓名字。读者答对了，解释是在确认他已经推断出的东西
     （记忆编码最牢固的时刻）；答错了，纠正发生在他自己推理投入之后
     （比被动接收深刻得多）。
   - 读者的回答要被记录进课程文件和 progress.json 的薄弱点分析里。
4. **逐要素回扣**：揭晓后，一条条对照——"故事里哪个情节对应了概念的
   哪一个核心要素"。让抽象解释锚定在具体情节上，而不是再给一遍定义。

## 三、变体与降级规则

- **文体替换**：纯抽象、无因果结构的概念（缺少角色、决策、后果）写不出好寓言，
  硬写会产出漂亮但无启发性的文字。此时换文体照亮概念的侧面：
  侦探小说（信息不对称）、来自未来文明的商业备忘录、神话、童话。
- **篇幅控制**：寓言不超过约 300 字，短版本更严苛地逼出概念核心。
- **读者画像**：故事要按摸底得到的基础来写——对有工程背景的读者和
  零基础读者，同一个概念该用完全不同的故事。
- **链式追问**：交付寓言后可以问"这个故事没能捕捉到概念的哪个方面？"
  这是 learn-review 的高级题型之一。
- **保存好寓言**：好的寓言是可长期复用的知识资产——所以 plan.md 里有
  "寓言与图索引"一节，随课程生成持续更新。

## 四、规划设计原则（learn-plan 的依据）

1. **从摸底结果决定起点**：大纲第一天的内容必须落在用户已有基础的正上方
   一小步，而不是教科书的第一章。
2. **知识点的寓言适配分级**：
   - `fable`：有因果结构——有角色（系统的哪个部分）、决策（参数/权衡）、
     后果（性能/正确性影响）。绝大多数机制、算法、博弈、经济学概念属此类。
   - `variant`：纯数学抽象、纯记号约定。标注替代文体。
   - `direct`：环境配置、语法、API 用法等操作内容。直接讲 + 动手做。
3. **配图选型规则**（配合本机 archify skill 的五种图型）：
   - 结构/组成/边界 → `architecture`
   - 数据怎么流、管道/ETL → `dataflow`
   - 步骤/审批/流程 → `workflow`
   - 参与方之间的交互时序 → `sequence`
   - 状态机/生命周期 → `lifecycle`
   - 一条经验法则：如果这个知识点在用户的脑中应该形成"一幅画面"，
     就配图；如果它本质是一段逻辑推理，寓言比图更有效，标 `none`。
4. **节奏**：每个知识点的过关标准写成可检验的行为（"能不看资料向别人
   讲清 X 的取舍"、"能给出一道新题的正确判断"），而不是"读完第 N 节"。
5. **里程碑**：每 3-5 天设一个综合检验点，learn-review 在里程碑日做
   跨知识点的综合测验，而不是单点测验。

## 五、测验设计原则（learn-review 的依据）

- 渐进加难四档：**回忆**（是什么）→ **应用**（新情境下怎么用）→
  **挑错**（这段论述哪里有漏洞）→ **反向费曼**（把这个定义还原成一个
  不点名的三段式故事，或指出已有寓言漏掉了概念的哪个方面）。
- 严苛但公平：直接指出理解偏差，不客套；但每指出一个薄弱点，
  都同时给出"回看哪一天的哪个寓言/哪张图能修复它"。
- 测验结果写回 progress.json（`mastery` 与 `weakPoints`），
  让后续课程的生成能主动绕开或重点加固薄弱处。
